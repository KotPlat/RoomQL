# RoomQl — Technical Specification

## Problem Statement

Android developers using Room have no first-party API for composing queries programmatically with compile-time safety. The two available workarounds — raw `@Query` SQL strings and combinatorial overloaded DAO methods — both break down as the number of optional runtime filter parameters grows. Raw strings fail silently on schema changes; overloaded methods grow quadratically and cannot represent open-ended filter combinations.

## Solution

RoomQl is a Kotlin library (three Gradle modules: `:annotations`, `:runtime`, `:ksp-processor`) that exposes a type-safe `query { }` DSL. KSP generates typed `Column<T>` companion properties from `@Entity` classes. The builder compiles to `SupportSQLiteQuery`, which Room's `@RawQuery` accepts. KSP also generates `@RawQuery`-wired DAO implementations for functions annotated with `@QueryFunction` (Mode A). Developers who want full `@RawQuery` control call the builder manually and pass the result themselves (Mode B). Both modes coexist in the same `@Dao` interface.

## User Stories

1. As a library consumer, I want to call `query { from(UserEntity) where { UserEntity.age gt 18 } }` and receive a `SupportSQLiteQuery`, so that I can pass it directly to a Room `@RawQuery` DAO method.
2. As a library consumer, I want `UserEntity.age` to be a `Column<Int>` generated by KSP from my `@Entity` class, so that renaming a column in my entity causes a compile error in my query rather than a silent runtime failure.
3. As a library consumer, I want `@ColumnInfo(name = "user_age")` to be respected in generated column refs, so that the DSL uses the actual SQL column name rather than the Kotlin property name.
4. As a library consumer, I want `@Embedded` fields in my `@Entity` to be flattened into column refs with their correct prefix, so that embedded properties are accessible in the DSL at the same level as top-level columns.
5. As a library consumer, I want null values passed to condition operators to cause that condition to be silently omitted, so that I can pass nullable variables without wrapping every condition in an `if` statement.
6. As a library consumer, I want `eq`, `notEq`, `gt`, `gte`, `lt`, `lte` typed infix operators on `Column<T>`, so that numeric and string comparisons are expressed idiomatically in Kotlin with full type safety.
7. As a library consumer, I want `like`, `notLike`, `contains` operators on `Column<String>`, so that SQL LIKE patterns are expressed without raw strings.
8. As a library consumer, I want `isNull()` and `isNotNull()` operators on any `Column<T?>`, so that nullable column checks do not require special handling.
9. As a library consumer, I want `inList(values: List<T>)` and `notInList(values: List<T>)` on `Column<T>`, so that SQL IN (...) clauses are expressed as Kotlin collections.
10. As a library consumer, I want `between(lower: T, upper: T)` on comparable `Column<T>`, so that SQL BETWEEN is a first-class operator without string interpolation.
11. As a library consumer, I want conditions inside `where { }` to be AND-combined by default, so that multi-condition queries read naturally without explicit `and` calls.
12. As a library consumer, I want `or { }` blocks inside `where { }` that collect their inner conditions as OR-combined, so that I can express OR-grouped predicates within an AND-default context.
13. As a library consumer, I want `orderBy(column, ASC|DESC)` to be chainable for multi-column sort, so that I can specify complex sort orders without raw SQL ORDER BY strings.
14. As a library consumer, I want `limit(n: Int)` and `offset(n: Int)` as sibling builder calls, so that pagination is expressed without string interpolation.
15. As a library consumer, I want `groupBy(column)` and a `having { }` block as sibling builder calls, so that aggregate queries with GROUP BY and HAVING are expressible in the DSL.
16. As a library consumer, I want `join(OrderEntity, JoinType.INNER) { on { UserEntity.id eq OrderEntity.userId } }` syntax for inner and left joins, so that multi-table queries are written without raw JOIN strings.
17. As a library consumer, I want unlimited chained `join` calls, so that I can join more than two tables in a single query.
18. As a library consumer, I want conflicting column names across joined tables to be automatically aliased in the generated SQL, so that I do not get silent data-overwrite bugs from column-name collisions.
19. As a library consumer, I want to provide my own result data class for JOIN queries, so that I control the shape and field names of joined results rather than receiving a library-generated type.
20. As a library consumer using Mode A, I want to annotate an abstract function inside an existing `@Dao` interface with `@QueryFunction` and have KSP generate the `@RawQuery` implementation automatically, so that I get type-safe dynamic queries with zero boilerplate.
21. As a library consumer using Mode A, I want the generated DAO implementation to be in the same package as my `@Dao` interface and named `RoomQl_<DaoName>`, so that Room's KSP processor can discover and compile it without extra configuration.
22. As a library consumer using Mode A with a `Flow<List<T>>` return type, I want KSP to infer `observedEntities` from my `from()` and `join()` clauses and populate `@RawQuery(observedEntities = [...])` on the generated implementation, so that reactive queries react to table changes without me declaring entities manually.
23. As a library consumer using Mode A with a `suspend` return type, I want the generated implementation to call the `@RawQuery` function as a suspend function, so that one-shot queries integrate with coroutine callers.
24. As a library consumer using Mode B, I want to write my own `@RawQuery fun rawSearch(q: SupportSQLiteQuery): List<T>` in a `@Dao` interface and call `query { }` in my repository to build the argument, so that I retain full control over the `@Dao` surface.
25. As a library consumer using Mode B with Flow, I want full manual control of `@RawQuery(observedEntities = [...])`, so that I can specify entities that are not inferable from a purely dynamic query.
26. As a library consumer, I want Mode A and Mode B functions to coexist freely in the same `@Dao` interface, so that I can adopt Mode A incrementally without rewriting existing Mode B methods.
27. As a library consumer, I want a KSP compile error when `@QueryFunction` is applied to a function on an interface not annotated with `@Dao`, so that misconfiguration is caught at build time.
28. As a library consumer, I want a KSP compile error when a `@QueryFunction` function returns `Flow` but the entities cannot be inferred from the DSL body, so that I know exactly what to declare before the app runs.
29. As a library consumer, I want a KSP compile error when a `@QueryFunction` function has an unsupported return type (e.g. raw `Cursor`), so that unsupported patterns fail loudly at build time with a clear message.
30. As a library consumer, I want runtime validation to be lazy, deferred to `build()`, so that a partially constructed `QueryBuilder` does not throw during the builder phase.
31. As a library consumer, I want runtime errors to be thrown as `RoomQlException : RuntimeException`, so that I can catch library errors specifically in tests and error handlers without catching unrelated exceptions.
32. As a library consumer, I want the library to support Android API 21+ with Room 2.6.x–2.7.x, so that it is compatible with the broadest Android device base.
33. As a library consumer, I want to add the library via JitPack with a single `implementation` line in `build.gradle.kts`, so that integration requires no local Maven repository or custom repository setup.
34. As a library consumer, I want the RoomQl KSP processor and Room's own KSP processor to run in the same `ksp()` invocation without conflict, so that I do not need separate KSP execution blocks.
35. As a library consumer, I want KSP-generated column ref files (`UserEntity_Columns.kt`) placed in the same package as my entity, so that column refs are usable without additional imports.
36. As a library consumer, I want a generated table-name companion property on each entity's generated columns file, so that the DSL can perform JOIN aliasing without developer-supplied table-name strings.
37. As a library consumer in a multi-module Android project, I want the DSL to live in `:core:query-dsl` and the Gradle dependency graph to enforce that only `:data` layer modules depend on it, so that the clean-architecture layer boundary is enforced at build time rather than by convention.

## Implementation Decisions

### Module Boundaries and Dependency Graph

Three Gradle modules, no inter-module cycles:

- **`:annotations`** — zero dependencies. Contains `@QueryFunction` annotation class. Both application-layer and data-layer modules may depend on this via `implementation`.
- **`:runtime`** — depends on `androidx.room:room-runtime`, `androidx.room:room-ktx`, and `androidx.sqlite:sqlite`. Contains the `QueryBuilder` DSL receiver, `Column<T>`, `Condition` hierarchy, `JoinType` enum, `SortDirection` enum, and `RoomQlException`. Only `:data` modules depend on this.
- **`:ksp-processor`** — depends on KSP API, KotlinPoet, `kotlinpoet-ksp`, and `:annotations`. Never a runtime dependency of application code; declared as `ksp(...)` only.

### `Column<T>` Type Contract

`Column<T>` is a value type (data class or value class) holding:
- `columnName: String` — the SQL column name (resolved from `@ColumnInfo` if present, otherwise the Kotlin property name)
- `tableName: String` — the SQL table name from the entity's `@Entity(tableName = ...)`, used for JOIN aliasing
- A type token (unused at runtime but constrains operator generic bounds at compile time)

`Column<T>` exposes the following infix operators returning `Condition`:
- `eq(value: T?)`, `notEq(value: T?)` — skipped when value is null
- `gt(value: T?)`, `gte(value: T?)`, `lt(value: T?)`, `lte(value: T?)` — on `Column<T : Comparable<T>>`
- `like(value: String?)`, `notLike(value: String?)` — on `Column<String>`
- `contains(value: String?)` — sugar for `LIKE %value%`, on `Column<String>`
- `isNull()`, `isNotNull()` — no argument; never skipped
- `inList(values: List<T>?)`, `notInList(values: List<T>?)` — skipped when null or empty
- `between(lower: T?, upper: T?)` — skipped when either bound is null

### `Condition` Hierarchy

`Condition` is a sealed type with subtypes for each SQL predicate. The DSL `where { }` block collects `Condition` values into an AND-combined list. `or { }` produces a single `Condition.Or` wrapping its inner list. Null-valued conditions are represented as `Condition.Empty` and are filtered out at `build()` time.

### `QueryBuilder` Receiver API

`query { }` is a top-level function whose receiver is `QueryBuilder`. `QueryBuilder` is not thread-safe and must not be shared across coroutines. Methods:

- `from(entity: KClass<*>)` — sets the primary table; must be called exactly once before `build()`
- `where(block: ConditionScope.() -> Unit)` — optional; AND-combined by default; multiple calls merge conditions
- `join(entity: KClass<*>, type: JoinType, block: JoinScope.() -> Unit)` — chainable; `JoinType.INNER` or `JoinType.LEFT`
- `orderBy(column: Column<*>, direction: SortDirection)` — chainable; appends to ORDER BY clause
- `limit(n: Int)` — sets LIMIT; must be positive or throws at `build()`
- `offset(n: Int)` — sets OFFSET; requires `limit` to be set or throws at `build()`
- `groupBy(column: Column<*>)` — sets GROUP BY column
- `having(block: ConditionScope.() -> Unit)` — sets HAVING conditions; requires `groupBy` or throws at `build()`
- `build(): SupportSQLiteQuery` — validates, serializes to SQL string, binds positional `?` args, returns `SimpleSQLiteQuery`

Binding uses positional `?` placeholders only. Named parameters are not supported (Room `@RawQuery` restriction).

### JOIN Aliasing Strategy

When two or more joined tables share a SQL column name, the DSL generates explicit `table.column AS table__column` aliases for all columns from joined tables in the SELECT clause. The developer's result data class fields must match these alias names if they are ambiguous. This is documented in the library README.

### Mode A — `@QueryFunction` Annotation Contract

`@QueryFunction` is applied to an abstract function inside a `@Dao`-annotated interface. The function body must be a `query { }` builder expression (enforced by convention, not by the compiler — KSP reads the function signature only). KSP generates a concrete class named `RoomQl_<DaoName>` in the same package, extending the `@Dao` interface, providing a `@RawQuery`-annotated implementation for each `@QueryFunction` function.

For `suspend` return types, the generated function calls Room's suspend `@RawQuery` overload. For `Flow<List<T>>` return types, KSP adds `@RawQuery(observedEntities = [EntityA::class, EntityB::class])` inferred from `from()` and `join()` entity arguments. Room's own KSP processor then compiles the generated class as a normal `@Dao` implementation.

### Mode B — Manual `@RawQuery` Contract

No annotation or generation involved. The developer declares `@RawQuery fun rawSearch(q: SupportSQLiteQuery): List<T>` in their `@Dao` interface and calls `query { ... }` in data-source or repository code, passing the result as the `q` argument. The developer is responsible for `@RawQuery(observedEntities = [...])` when returning `Flow`.

### Error Model — KSP Compile Errors

All KSP errors use `KSPLogger.error(message, symbol)` pointing at the annotated declaration site. Error message prefix: `"RoomQl: "`. Required checks:

- `@QueryFunction` on non-`@Dao` interface → `"RoomQl: @QueryFunction can only appear inside a @Dao interface."`
- `@QueryFunction` returning `Flow` without inferable entities → `"RoomQl: Cannot infer observedEntities for Flow return type. Add explicit from() or join() clauses, or use Mode B with manual @RawQuery."`
- `@QueryFunction` with unsupported return type → `"RoomQl: Unsupported return type '<type>'. Supported types: List<T>, suspend List<T>, Flow<List<T>>."`
- `@QueryFunction` on function with no return type → `"RoomQl: @QueryFunction function must declare a return type."`

### Error Model — Runtime Exceptions

`RoomQlException : RuntimeException`. All validation is lazy, deferred to `build()`. Thrown cases:

- `from()` not called before `build()`
- `limit` set to a value ≤ 0
- `offset` set without `limit`
- `having` called without `groupBy`

### KSP Code Generation Tooling

KotlinPoet + `kotlinpoet-ksp` for all generated source. No raw string templates. Aggregating KSP mode required (entity discovery must see all source files before generating JOIN alias logic). Generated files:

- Column refs: `<EntityName>_Columns.kt` in the same package as the entity
- Mode A DAO impl: `RoomQl_<DaoName>.kt` in the same package as the `@Dao` interface

KSP minimum version: `1.9.20-1.0.14` (aligns with Room 2.6's Kotlin 1.9 line).

### Room Version Pin

Room 2.6.x–2.7.x (≤ 2.7.x). Room 2.8.0 raised `minSdk` to API 23; the library targets API 21+. This pin is documented in the library README and enforced via `compileOnly` bounds in `:runtime`.

### Publishing

JitPack, GitHub-tag-based release. SemVer tags (`v1.0.0`, `v1.0.1`, ...). The README documents the three dependency declarations a consumer must add: `implementation(annotations)`, `implementation(runtime)`, `ksp(ksp-processor)`.

## Testing Decisions

### What Makes a Good Test

A good test asserts the observable external contract of a module — the SQL string and positional argument list produced by `build()`, or the source text of KSP-generated files — not internal builder state or private implementation details. Tests must not reach into `QueryBuilder` fields, `Condition` subtypes, or KSP symbol tables. Every test must be reproducible on the JVM without a running Android device.

### Primary Seam — `SupportSQLiteQuery` Output (`:runtime`, pure JVM)

The single output interface of the `:runtime` module is `SupportSQLiteQuery` (concretely `SimpleSQLiteQuery`). Tests at this seam exercise the entire DSL surface. Each test calls `query { ... }` and asserts `.sql` (the SQL string) and the ordered positional argument list (extracted via `SimpleSQLiteQuery.argCount` and the bound args array). Coverage required:

- One test per operator variant (`eq`, `gt`, `inList`, `between`, `contains`, `isNull`, etc.)
- AND-default combinator
- `or { }` group within `where { }`
- Multi-column `orderBy` chain
- `limit` and `offset` together
- `groupBy` + `having`
- INNER JOIN and LEFT JOIN with auto-aliasing
- Null value → condition omitted (one test per nullable operator)
- `build()` throws `RoomQlException` for each invalid state (no `from`, negative `limit`, `offset` without `limit`, `having` without `groupBy`)

### Secondary Seam — KSP-Generated Source Files (`:ksp-processor`, JVM compilation harness)

Use `kotlin-compile-testing-ksp` (Tschuchort's compilation testing library). Each test provides source files containing `@Entity` or `@QueryFunction` annotations, runs the RoomQl KSP processor, and asserts the content of generated files. Coverage required:

- Column name resolved from `@ColumnInfo(name = ...)` vs. Kotlin property name
- `@Embedded` field flattening with prefix
- Table-name companion property generated correctly
- Mode A: generated class name, package, `@RawQuery` annotation present
- Mode A + `Flow`: `observedEntities` populated from `from()` and `join()` entities
- Mode A + `suspend`: generated function is `suspend`
- All four KSP compile-error paths produce the correct error message string

### No Android Instrumented Tests Required for the Library

The library's own test suite runs entirely on the JVM. The sample app bundled in the repo serves as the manual end-to-end integration harness for verifying behavior against a real in-memory Room database.

### Prior Art for Tests

No existing tests in the repo. The `kotlin-compile-testing-ksp` pattern is established in the Kotlin annotation-processing community (Room's own processor tests, Dagger's KSP tests) and is the reference model for the `:ksp-processor` test suite.

## Out of Scope

- Replacing Room's compile-time `@Query` validation — RoomQl handles the dynamic query case only; static queries remain as `@Query`.
- Supporting non-Room databases (SQLDelight, raw SQLite, Realm, any JDBC-based ORM).
- An IDE plugin or language injection for the DSL.
- A Gradle plugin for automatic multi-module wiring (deferred to v2).
- Pagination integration with `androidx.paging` — `LIMIT/OFFSET` stays raw.
- KSP-generated result types for JOIN queries — the developer supplies their own data class.
- Room 2.8.0+ support (minSdk 23 requirement; deferred until the API 21 constraint is relaxed).
- SNAPSHOT / pre-release publishing workflow.
- Cross-column type-safety enforcement in JOIN `on` clauses (e.g. preventing `StringColumn eq IntColumn` at compile time via generic bounds — deferred to v2 if feasible).

## Further Notes

- The closest prior art, `AniTrend/support-query-builder`, uses bare `String` column refs. RoomQl's typed `Column<T>` is the primary differentiator.
- jOOQ's `noCondition()` seed pattern and Ktorm's `whereWithConditions {}` block form informed the null-skipping and combinator design.
- The silent JOIN column-name collision bug (row data silently overwrites when two joined tables share a column name in a `@RawQuery` result cursor) is addressed by the DSL's automatic aliasing. This is a known Room `@RawQuery` footgun documented in ticket 001.
- `@Transaction` is required alongside `@RawQuery` when the query uses `@Relation`. This is a Room constraint that RoomQl documents but does not enforce; violating it is a Room compile error, not a RoomQl concern.
- Room's observable `@RawQuery` with `observedEntities` guarantees the same invalidation behaviour as `@Query` returning `Flow`. This was confirmed as stable from Room 2.2.0 (ticket 001).
- KSP aggregating mode is non-negotiable: incremental per-file processing cannot see all entities simultaneously, which is required for detecting cross-entity JOIN column conflicts.
